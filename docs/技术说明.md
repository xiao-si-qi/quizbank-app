# 技术说明

面向要改这份代码的人。

## 模块划分

```
:core   纯 Kotlin/JVM，不引用任何 Android API
:app    Android 壳 + Compose UI
```

`:app` 依赖 `:core`，反向不成立。这条约束是刻意的：

1. **单元测试快**。`core` 的测试跑在真正的 JVM 上，不需要 Robolectric、不需要模拟器，
   85 个测试 30 秒内跑完。
2. **不可能偷偷依赖 Android**。想 import `android.*` 会直接编译失败。
3. **将来换平台是机械操作**（见文末）。

`core` 里的包：

| 包 | 职责 | 依赖 |
|---|---|---|
| `excel` | XLSX 读写、CSV(GBK) 解析 | 只用了 `java.util.zip` 与 `javax.xml.parsers` |
| `importer` | 表头容错匹配、题目/题库列表解析、模板生成 | 只依赖 `excel` |
| `alist` | alist v3 API 客户端、地址归一化、登录会话 | OkHttp |
| `rich` | 图文混排解析（Markdown / HTML / 裸链接） | 无 |
| `image` | 图片本地缓存、预下载、LRU 清理 | OkHttp + `alist` |
| `score` | 成绩模型、上传、云端汇总 | 无 |
| `domain` | 判分、组卷 | 无 |
| `data` | 存储接口 / 设置接口 / 题库仓库 | 只依赖接口 |

`:app` 里只放三样东西：SQLite 实现、SharedPreferences 实现、Compose UI。

## 几个关键决策

### 1. 不用 Apache POI，自己写 XLSX 引擎

Apache POI 是 Java 桌面端的标准选择，但在 Android 上：

- `poi-ooxml` 依赖 `java.awt`（画图、字体度量），Android 没有；
- 依赖 `javax.xml.stream`（StAX），Android 也没有；
- 光 jar 就 10MB+，方法数会直接把 dex 撑爆。

而 XLSX 本质就是「一个 zip + 几个 XML」。`XlsxReader` 用 `ZipInputStream` 取出
`workbook.xml` / `sharedStrings.xml` / `styles.xml` / `worksheets/*.xml`，
再用 `javax.xml.parsers` 的 SAX 流式解析（`android.util.Xml` 在桌面 JVM 上不可用，
所以选了 `javax.xml.parsers`，两边都能跑）。

用 SAX 而不是 DOM 的原因：题库动辄上万题，DOM 会把整份 XML 载入内存并放大十倍以上。

已经处理的坑：

- 共享字符串、内联字符串、富文本 run（`<r><t>`）、公式结果（`t="str"`）、布尔、错误值
- 日语注音 `rPh` 要排除，否则会串进题干
- 合并单元格（题库列表常拿它做「分类」）会把左上角的值填满整个区域
- 日期序列号按 `cellXfs` 的 `numFmtId` 判断，并处理 1900 年闰年 bug
- 数字 `1` 不能变成 `1.0`，否则答案比对会出错
- 写出时用 `inlineStr` 免去 sharedStrings 表，并过滤 XML 非法控制字符

写出的模板文件本身就会被测试用同一个读取器读回来，保证「模板」与「能读的格式」永远一致。

### 2. 不用 Room

六张表、结构简单，手写 `SQLiteOpenHelper` 少一层 KSP 注解处理器，
构建更快、出问题也更好排查。题目数据随时能从 alist 重新下载，所以升级策略直接重建表。

重新导入题库时**不是**先删后插，而是按「同一顺序 + 题干一致」配对，再按题干兜底配对，
配不上的才新增、多余的才删除。这样收藏、错题、答题记录的 `question_id` 都还指得对，不会丢。

### 3. 容错导入

`ColumnMatcher` 先用**别名精确匹配**，再退化成包含匹配，一列只归一个字段、一个字段只占一列，
并按匹配强度排序（所以「答案解析」不会被「答案」抢走）。

另外两个实际踩过的坑：

- **表头行误判**：某张表第一行是表头，第二行数据里恰好有「甲题库」（含「题库」）和
  「备注文字」（含「备注」），候选分数反而更高。现在含 `/` 或 `http` 的行直接不参与表头评选。
- **全角转换**：`TextNorm.value()` 曾经做全角转半角，结果题干里的「？」被改成了「?」。
  现在全角转换只用于「比较」与「表头匹配」，展示用的文本原样保留。

### 4. alist 集成

- `FileRef` 把用户可能粘贴的三种地址统一成 `Direct`（可直接 GET）或 `AlistPath`（走 `fs/get` 换签名直链）：
  alist 路径、`/d/` 直链、浏览器地址栏里的页面链接。
- `AlistSession.withAuth` 在 token 失效（401）且存有账号密码时静默重登一次，
  用户放几个月再打开也不会被登出。
- 所有错误都翻译成中文可操作提示：返回 HTML 说明服务器地址填错、404 说明路径不存在、
  401 说明需要登录。

### 5. 图片

图片不能直接交给图片库加载 URL：私有 alist 需要 token 或临时签名，而且用户下载题库后期望离线能看图。
所以统一走「先查本地缓存 → miss 就带鉴权下载 → 落盘 → 交给 UI」，
`ImageStore` 用「题库目录 + 引用」的 SHA-1 做键（否则两个题库里的 `1.png` 会串图），
并做 LRU 清理。

### 6. 成绩与权限

成绩写成「一次练习一个 JSON」而不是往一张总表追加，这样多设备并发上传不会互相覆盖，
汇总放到客户端做。

权限完全交给 alist：管理员账号能列出成绩目录下所有用户的子目录，普通用户只能看到自己被授权的路径。
App 端不做任何额外鉴权，也不预取别人的数据。

## 普通用户零配置是怎么做到的

面向普通用户的 App，最怕一上来让人填服务器地址、路径、Token。这里的做法是：

1. **所有路径都有默认值**，写在 `AppSettings` 的伴生对象里
   （默认服务器、公开题库清单、完整题库清单、成绩目录名）。
2. **路径跟着登录状态自动切换**：`AppSettings.withAutoDefaults(account)` 一个纯函数搞定——
   未登录 → 公开清单、无成绩目录；已登录 → 完整清单、成绩目录指向**共用的成绩根目录**
   （`/题库/成绩`）。
   用户一旦手动改过路径，`autoConfigurePaths` 就置 false，之后不再自动覆盖。
3. **首次启动自动取题库**：`HomeViewModel.bootstrapIfNeeded()` 发现本地没有题库就自己去拉，
   先按设置拉、失败再用另一份清单兜底；都失败且开关打开时，才载入内置示例题库。
4. **Token 不出现在界面上**：登录页只有服务器地址/用户名/密码三个字段，
   token 由 `AlistSession.login()` 拿完直接存本地，过期还会静默重登。

副作用是设置页简单了很多：账号区只剩「服务器地址 + 登录/退出 + 测试连接」。

## 测试策略

`core` 的测试覆盖了真正容易出错的地方：

- XLSX 引擎：写出再读回、共享字符串/富文本/rPh、合并单元格、日期格式、特殊字符
- CSV：GBK/UTF-8/BOM、分隔符探测、引号内逗号与换行
- 解析器：表头别名与乱序、题干内嵌选项、答案的各种写法、题型推断、多工作表、异常提示
- alist：用 MockWebServer 校验登录、匿名请求不带鉴权头、上传的 `File-Path` 是否 URL 编码、
  `role` 数组与数字两种形态、401/HTML 的错误翻译
- 判分：五种题型、多选顺序无关、空数不一致、主观题不自动判分
- 端到端：App 自己生成的模板 → App 自己的解析器读回

```bash
./gradlew :core:test
```

UI 层没有自动化测试（需要真机/模拟器），所以关键交互都做了防御性处理。

## 将来要上 iOS / 桌面怎么办

推荐 **Kotlin Multiplatform + Compose Multiplatform**，因为业务逻辑已经全在 `core` 里且不依赖 Android，
迁移只需要替换三样东西：

| 现在 | 换成 | 影响面 |
|---|---|---|
| `app/data/db/SqliteQuizStore.kt` | SQLDelight | 一个文件 |
| `app/data/prefs/SettingsStore.kt` | multiplatform-settings 或 DataStore | 一个文件 |
| `core/alist` 里的 OkHttp | Ktor Client（或保留 OkHttp 只在 JVM/Android 用） | 一个文件 |

`core` 里的 `excel` 需要的 `java.util.zip` 与 `javax.xml.parsers` 在 Kotlin/Native 上不存在，
要换成 okio 的 zip 与 `xmlutil`，大概一两天工作量；`importer` / `domain` / `score` / `rich` 完全不用改。

UI 那边 Compose Multiplatform 已经可以覆盖 Android / iOS / 桌面，
但 **Web(Wasm) 仍是 alpha**——如果跨平台清单里有浏览器，那一块建议单独用 Web 技术栈做，
而不是硬塞进 KMP。

如果团队更熟悉 TypeScript，另一个可行选择是 Flutter（逻辑+UI 全复用，代价是全量重写）
或 Capacitor/Tauri（Web 前端 + SheetJS，逻辑复用最好但原生能力最弱）。
以这个项目的形态（重逻辑、轻原生能力、无后端），KMP 的性价比最高。

### 成绩目录为什么用绝对路径

早期版本按账号的 `base_path` 算成绩目录，结果管理员的 `base_path` 是 `/`，
目录被算成 `/成绩/用户名`（落在 alist 根目录），而上传时又拼了一次用户名，
最终传到了 `/成绩/用户名/用户名/` —— 管理员反而看不到别人的成绩。

现在统一用绝对路径 `/题库/成绩` 作为**所有人共用的成绩根目录**，
具体到某个用户的子目录由 `ExamRepository.myDir()` 在根目录下拼一次用户名。
账号 `base_path` 的换算交给 `AlistClient.requestPath()`：
调用方只管传绝对路径，客户端会把与 base_path 重合的前缀剥掉再发请求。

`AppSettings.repaired()` 会在启动时把历史遗留的错误路径改回来。
